# ADR-0005: المصادقة

- **التاريخ:** 2026-10-10 · **المالك:** المهندس المسؤول · **الحالة:** معتمد

**القرار:** **Better Auth** مكتبة داخل الخلفية، وبياناتها في قاعدتنا: بريد متحقق، وجلسات خادم آمنة (HttpOnly وSecure وSameSite)، وإضافة المؤسسات (organization) للعضويات والدعوات، وتحقق ثنائي TOTP للمالك والمعتمدين.

**الخيارات:** Clerk (مزود خارجي)، أو Auth0، أو Neon Auth المُدار، أو Better Auth داخلي.

**السبب:** البيانات تبقى في قاعدتنا، وهذا مهم لبوابة موقع البيانات (ADR-0003). ولا نبني تخزين كلمات مرور مخصصًا (القسم 10). ونموذج المؤسسات والدعوات يناسب القسم 8.

**الأثر:** الصلاحيات الدقيقة (`metrics.read` و`costs.write`...) تُبنى طبقةً فوقه في وحدة Identity/Tenancy، ولا تُعتمد على أدوار المكتبة وحدها. والدعوة صالحة لمدة محددة واستخدام واحد.

## تنفيذ (2026-10-10)

- جداول Better Auth بأسماء snake_case في الترحيل `0003_auth_identity.sql`، واختبار آلي (`getMigrations`) يثبت أن المخطط مطابق لما تتوقعه المكتبة.
- **دور مستقل `arso_auth`** لجداول الهوية والجلسات فقط، ولا يرى أي بيانات مؤسسة. ودور التطبيق `arso_app` فقد القراءة العامة لجدول `users`.
- إنشاء المؤسسة وقبول الدعوة عبر دوال `SECURITY DEFINER` فقط (`create_organization` و`accept_invitation`). دور التطبيق لا يملك `INSERT` على المؤسسات أو العضويات.
- الدعوة: رمز 256 بت يُرسل بالبريد مرة واحدة، وتُخزن تجزئته SHA-256 فقط، وصلاحيتها 72 ساعة (قابلة للضبط)، وتُقبل مرة واحدة، وللبريد المقصود فقط.
- الواجهة والـ API من نفس الأصل عبر وكيل Next (`/api/*`)، فكوكي الجلسة `HttpOnly` و`SameSite=Lax` و`Secure` في الإنتاج.
- التحقق الثنائي (TOTP) مفعّل في الخادم، وواجهته تُبنى مع بوابة E2 (اعتماد الإنفاق).

# ADR-0003: الاستضافة

- **التاريخ:** 2026-10-10 · **المالك:** المهندس المسؤول والمالك · **الحالة:** معتمد للاختبار (staging)؛ الإنتاج مشروط

**القرار (بيئة الاختبار والتطوير):**
| الخدمة | المزود | المنطقة |
|---|---|---|
| الواجهة والخلفية والعمّال | Railway | EU West (أمستردام) |
| PostgreSQL | Neon | `aws-eu-central-1` (فرانكفورت) |
| تخزين الملفات | Cloudflare R2 (متوافق مع S3) | أوروبا |
| الأخطاء والأداء | Sentry | ألمانيا (`de.sentry.io`) |

**لماذا Railway؟** يشغّل عدة خدمات من monorepo واحد (web وapi وworker) بشبكة خاصة بينها، ومهام مجدولة، ونشر من GitHub، والفريق يستخدمه أصلًا مع عزو. Render بديل مكافئ، لكن Railway أبسط للخدمات المتعددة.

**لماذا Neon؟** فرع قاعدة بيانات مستقل لكل طلب دمج، فنختبر الترحيلات والعزل على نسخة حقيقية قبل الدمج. واستعادة لنقطة زمنية (PITR) تحقق هدف RPO ≤ ساعة في القسم 49.

**لماذا أوروبا؟** أقرب منطقة متاحة للسعودية لدى Neon هي فرانكفورت، وRailway في أمستردام قريب منها، فيكون التأخير بين الخادم والقاعدة منخفضًا.

**بوابة الإنتاج (القسم 47):** قبل دخول بيانات شخصية حقيقية لعملاء المتاجر، يراجع مختص متطلبات نظام حماية البيانات الشخصية السعودي ونقل البيانات. إن تطلّب ذلك الاستضافة داخل المملكة، ننقل الإنتاج إلى مزود سحابي بمنطقة سعودية (مثل Google Cloud الدمام). البنية مبنية بحيث يكون النقل تغيير إعدادات لا إعادة بناء: حاويات Docker، وPostgreSQL قياسي، وتخزين متوافق مع S3.

**الأثر:** بيئة الاختبار تعمل ببيانات اصطناعية ومتجر اختبار فقط، ولا تُنسخ إليها بيانات حقيقية كاملة (القسم 50).

## ملاحظة تنفيذية (2026-10-10)

- مشروع Neon: `arso` (`divine-cherry-93627619`) في `aws-eu-central-1`، وPostgreSQL 16، والفرع `main`، والقاعدة `arso`.
- الترحيلات 0001 و0002 مطبقة، وRLS مفعّل ومفروض (FORCE) على كل الجداول.
- **تحذير أمني:** دور المالك في Neon (`arso_owner`) يملك `BYPASSRLS`، لذلك **لا يتصل التطبيق به أبدًا**. التطبيق والعمّال يتصلون بدور `arso_app` فقط، ويُفعَّل دخوله بكلمة مرور عند النشر. `arso_owner` للترحيلات فقط، وكلمة مروره تُدوَّر قبل أول نشر.
